# Technical backlog

[Documentation index](../README.md#documentation)

This is the agreed hardening roadmap for bringing QuickAPI-Express up to the engineering safeguards used in QuickAPI-NestJS, scaled to this application's existing scope. Entries distinguish completed engineering work from remaining backlog items and deployment-owned verification.

The initial source review was against Express commit `6947b772cde9d445f5a02d8a5c282e65a7c959bf`. Recheck the implementation before starting each item. The existing CI gate remains useful evidence, but does not establish that these failure paths are protected.

## Scope and agreed contracts

- Harden existing item operations, HTTP policies, persistence, diagnostics, and release checks. New business features, authentication, audit-history functionality, queues, and provider integrations are outside this roadmap.
- Add a numeric item `version` and require `expected_version` for PUT, PATCH, and DELETE. Updates must atomically compare the expected revision and advance it once; stale requests return `409` without mutation. Deletion must atomically compare the expected revision before removing the row.
- Use `expected_version` in update bodies. Decide its DELETE transport before implementation: the current middleware rejects DELETE bodies. Document the chosen transport and client migration explicitly.
- Start optional `Idempotency-Key` support with POST item creation. Extend to other mutations only after defining a concrete replay benefit and contract for each operation.
- Define idempotency scope for this public API before implementation. NestJS's authenticated-actor scope cannot be copied unchanged; do not introduce authentication or use an IP address as client identity implicitly.
- Keep concurrency and replay protection independent. Versions prevent stale writes; idempotency prevents duplicate execution. An identical completed keyed retry replays its original response without another mutation or version increment.
- Review other behavior changes explicitly before implementation. Revision requirements are an intentional request/response contract change, requiring migrations, OpenAPI updates, client coordination, and rollback planning.

Deliver the milestones in order, with focused regression tests alongside each change rather than postponing tests until the final milestone.

### Completion review and remaining boundaries

The post-merge review found and corrected one response-deadline edge case:
`res.end()` must not disable the deadline while the final write is still pending.
Focused regressions also cover credentials on CORS preflight/actual responses,
late controller lookups before mutations, a real blocked MySQL write completing
after an HTTP timeout, a late probe acquisition after shutdown, and concurrent
limiter requests. Follow-up review changes need their own CI run when committed;
the linked CI evidence applies to the merged baseline above.

Remaining deployment verification is explicit: test the real ingress trust boundary
and client IPs, browser CORS behavior through that ingress, orchestrator traffic
withdrawal and termination grace, and environment-specific database failover/TLS.
These checks are not represented as completed production evidence by loopback,
controlled fault, or disposable-container tests. Shared rate limiting remains a
separate deployment decision. A response timeout does not cancel a database write.

| Data and query contracts | Price validation and MySQL decimal storage need an explicit precision/rounding contract. For keyed operations, a completed identical retry returns the original response snapshot, not a projection of the current item. A changed payload under the same unexpired key must conflict. Failed validation or a rolled-back transaction must not leave a successful replay record. Expiry and physical cleanup are separate concerns; define retention and bound response storage.

## Completion and release boundaries

For each item, record the implementation, focused regression evidence, and any contract/deployment impact. Distinguish passed, failed, skipped, and unavailable checks. Update the API, development, testing, and deployment guides when the implementation changes; do not describe planned behavior as already available.

Before calling a candidate release ready, require CI for its exact commit and verify deployment-specific proxy/CORS settings, operational access, database TLS and pool sizing, backup restore, and outage recovery. Disposable CI infrastructure does not establish those environment-owned conditions.
